# xFarm Reuse & Learn — AncientGroveOS

**For:** Khalaf single-estate heritage olive-grove manager (manager + one ops manager + seasonal crew).
**Not:** a multi-farm SaaS. Every recommendation below is filtered through that constraint.
**Repo state confirmed:** `lib/db/schema.ts` (single file, 14 tables); routes under `app/` as listed in context.

## 2. What we already match

Being specific — where AncientGroveOS is at or above xFarm's free tier today:

- **Parcel/crop/land registry → FULL match, arguably better.** `groves` (boundary, areaHa, slope, orientation, terraces, soilProfile) + `trees` (per-tree code, PostGIS point, crownPolygon, variety, ageEstimate, ancient flag, verificationStatus). xFarm registers *fields*; we register *individual trees*. Routes `/groves`, `/groves/[code]`, `/trees`, `/trees/[code]`, `/manager/map`.
- **Latest-NDVI-per-block (Satellite LITE equivalent) → matched.** `treeSatelliteObservations` stores NDVI/GNDVI/SAVI + healthIndex + anomalyFlags per tree per acquisition; `imageryAcquisitions` holds source/date/resolution; raster overlays render on `/manager/map`. **Gap vs LITE:** ours is per-tree points, not a rendered index heatmap; and it's single-date (see §3).
- **Weather (free tier) → matched and exceeded on history.** `groveWeatherDaily`, `groveWeatherSeasonSummary`, `rainEvents` (Open-Meteo ERA5, 45 seasons) with first-rain / dry-spell / heat-day derivations, surfaced at `/manager/climate`. xFarm's *free* weather is just current conditions; we have far deeper history. **Gap:** no forward forecast, no spray-window advice.
- **Grove memory / "every action is a data point" → partially matched.** `auditEvents` is append-only with before/after JSON deltas and actor — exactly the immutable-event pattern xFarm's Agent produces. `logTreeObservation` writes category/severity/note here. **Gap:** it captures *state changes*, not *planned actions/treatments*, and advice is not yet an event type.
- **Evidence accumulation → schema exists, unused.** `heritageRules` + `ruleEvidence` (recordType/recordId/contribution) can link any observation to a rule. This is our version of "recommendation → data point." Rules are seeded (9); evidence is not actively collected in workflows. Route `/manager/rules`.
- **Photo capture + review queue → matched at the ingest level.** `media` (purposeTag incl. pest/disease/pruning_before-after, EXIF, GPS, match states) + GPS-proximity matching + `/photos/upload`, `/photos/review`. **Gap:** matching is GPS-only — no vision, no classification, no confidence beyond proximity.

## 4. What to explicitly NOT copy

**Multi-farm-SaaS choices that are wrong for one estate:**

- **Tiered free/paid gating.** xFarm gates spray-timing and time-series behind PRO because it's a business model. We have one customer (you). Build the *actionable* features directly; there is no upsell to protect.
- **VRA prescription maps + ISOXML/Shapefile/John Deere export.** No variable-rate sprayer, no ISOBUS fleet. Skip the entire precision-ag interchange layer. If per-tree rates ever matter, GeoJSON is enough.
- **Warehouse/inventory movements with auto-decrement.** Over-modeled for one shed. A free-text product/dose field on the `treatments` row is sufficient.
- **Machinery telemetry / 70+ integrations / AgRouter.** Zero relevance. A machinery *name* on an activity row is the whole requirement.
- **Sensor hardware buildout (xSense/xNode/xLeaf).** Tempting, but the loop matters more than the hardware. Manual phone-photo trap counts + free ERA5/Open-Meteo weather drive rows 3/5/6 with no capex. Add hardware only if a specific model demands leaf-wetness you can't proxy.
- **Custom notification library / alert marketplace.** We need ~3 alerts (frost, dry-spell escalation, pest-generation emergence), not a configurable engine.

**Honesty & vocabulary guardrails (keep these — they are the heritage-brand differentiator):**

- **Satellite = signal, not diagnosis.** NDVI/NDRE anomaly means "look here," never "this tree is diseased." Our `anomalyFlags` + `recommendedAction` must stay phrased as *investigate*, not *conclude*. xFarm's marketing blurs this; we won't.
- **Estimate, not measurement.** `ageEstimate`, synthetic `healthIndex` (0–100), ERA5 weather (~25 km grid, *modeled* not in-situ), crown area *computed* from polygon. Every derived number keeps its provenance and its hedge. Do not let a health index masquerade as ground truth.
- **Vision confidence is a routing tool, not a verdict.** Row 7's "89.5% peacock spot" is a *prompt to inspect*, logged for your confirmation — never an auto-applied diagnosis on a heritage tree.
- **Anomaly = deviation from the tree's own baseline**, not a global threshold. A Souri on a steep dry terrace has a legitimately different NDVI than one on a valley floor. Per-tree/per-block baselining (row 2) is the honest method; a fleet-wide threshold is not.

## 5. Recommended sequence

Mapped onto the existing Phase roadmap. **New table** = schema migration in `lib/db/schema.ts`; **Pure UI** = routes/components only.

**Phase 1 — The record layer + free wins (the honest MVP)**
- Row 3 **GDD olive-fly forecast** — *new small table* (`gddAccumulation`), reads existing `groveWeatherDaily`. Card on `/manager/climate`. Start here: days, not weeks.
- Row 1 **Treatments/activities log + advice-as-event** — *new table* (`treatments`), reuse `auditEvents`/`ruleEvidence` patterns. This is the spine everything else writes to.
- Row 8 **Logbook export** — *pure UI/API* once row 1 lands.
- Activate `ruleEvidence`: have rows 1 and 3 write evidence links so the 9 seeded heritage rules start accumulating support/contradiction.

**Phase 2 — Low-friction capture + monitoring**
- Row 4 **WhatsApp/voice entry** — *pure UI/API* (`/api/agent/whatsapp`), writes to row 1's table. Gate on the WhatsApp-number decision.
- Row 6 **Trap counting** — *new tables* (`traps`, `trapCounts`), reuses `media`.
- Row 7 **Photo disease/pest detection** — *pure UI* extension of `/photos/review`; verdicts to `auditEvents`.
- Row 5 **DSS risk + protection degree** — *mostly logic*, one thin derived-events surface; needs 1+3+6 present.

**Phase 3 — Temporal intelligence (the flagship)**
- Row 2 **Satellite time-series anomaly** — *schema extension* (multi-acquisition ingest, rolling-baseline columns/materialized view, NDRE band) + significant new UI (time slider on `/manager/map`, trend panel on `/trees/[code]`) + a scheduled Sentinel-2 ingest job. This is the "grove has a memory" payoff and the largest single build — do it last, on top of a proven record layer.

New tables total: `treatments`, `gddAccumulation`, `traps`, `trapCounts` (+ satellite baseline columns). Everything else is UI/API or logic on tables you already have.

## 6. Open questions for the owner

1. **Satellite time-series feed (gates Row 2, the flagship).** Copernicus Sentinel-2 is free (~5-day revisit, 10 m) via Sentinel Hub / Google Earth Engine. Are we willing to stand up a scheduled ingest against it, or do you want a paid managed feed? Row 2 is dead without multi-date ingest — this is the highest-leverage decision.
2. **WhatsApp Business number (gates Row 4).** Is a dedicated WhatsApp Business API number (or a Twilio number) acceptable and obtainable for the estate? If not, the voice-first field entry falls back to a mobile web form (much higher friction for the crew).
3. **Which pests/diseases matter for Souri in the Galilee (gates Rows 3, 5, 6, 7).** Confirm the target list. Presumed primary: **olive fruit fly (*Bactrocera oleae*)** for the GDD/trap DSS; **peacock spot (*Spilocaea oleagina*)**, **olive knot**, and **Xylella/*Philaenus spumarius* vector** for photo diagnosis. We need the biofix date + base temperature + degree-day threshold for the fly to make Row 3 real.
4. **Certification intent (gates Row 8's priority).** Are we pursuing PDO/DOP or organic certification? If yes, the compliance-export format has specific requirements and Row 8 rises in priority; if no, it's a nice-to-have.
5. **Who logs, and on what device (shapes Rows 1 & 4).** Does the ops manager carry a phone with signal in the groves? Is there offline dead-zone coverage we must queue against? This decides whether the notebook is online-only or needs an offline queue.
6. **Trap operating model (shapes Row 6).** Manual weekly phone-photos of sticky/delta traps (zero capex, chosen build) vs. eventual camera traps — confirm we start manual.
